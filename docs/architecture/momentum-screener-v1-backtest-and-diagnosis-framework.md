## 2. 框架目标

这份文档要解决的不是“回测最后赚没赚钱”这么单一的问题，而是要回答 4 个更底层的问题：

1. 这套筛选方法到底有没有真实增量价值。
2. 如果结果不好，问题出在候选池、排序、买点，还是总闸门。
3. 如果市场环境变化，系统是否还能保持有效。
4. 如果系统表现变差，后续应如何基于回测结果做受控进化。

一句话总结：

**V1 回测不是只看收益，而是要建立一套能定位问题层级、验证决策质量、支撑后续进化的诊断框架。**

## 3. 回测前提：先冻结生产基线

V1 回测必须建立在一套固定生产基线上，不能边测边改入口。

当前 V1 基线固定为：

- 市场范围：主板 + 创业板 + 科创板
- 候选池统一入口：`最小涨幅 5% / 最小成交额 3亿 / 最小换手率 3%`
- 官方生产引擎：`Standard`
- `Aggressive`：进攻补充引擎，不作为 V1 官方最终裁判
- 返回数量：只影响页面展示，不影响二次决策本身

回测记录中必须显式冻结：

- `engine_profile`
- `engine_version`
- `entry_baseline_version`
- `market_scope_version`

没有固定基线，任何“系统胜率”“策略健康”“自动进化”结论都不具备可比性。

## 4. 回测对象：完整决策链，而不是单一得分

V1 回测对象不是某一个 `rank_score`，而是整条链路。

每个交易日 `T` 必须冻结记录以下四层决策：

### 4.1 日级决策

- 今日出手级别
- 推荐上限
- 是否生成行动清单
- 次日盘中是否允许发“建议买”信号

### 4.2 组合级决策

- 主仓 / 次仓 / 观察仓
- 默认组合的主线归属
- 每只票在组合中的角色

### 4.3 个股级决策

- 是否进入候选池
- 是否进入完整排序集 Top10 / Top3
- 是否被二次决策选中
- 入选或落选主因

### 4.4 执行级决策

- 买点区间
- 触发条件
- 追高上限
- 失效位
- 次日盘中最终收口结论

## 5. 回测方式：按交易日完整回放

V1 回测必须使用“交易日逐日回放”。

对每个历史交易日 `T`，严格只使用 `T 日收盘后可见信息`，完整运行一次：

1. 全市场统一筛出候选池
2. 对候选池做完整评分排序
3. 运行二次决策
4. 输出今日出手级别、组合、买点和行动清单
5. 再用 `T+1 / T+2` 的真实结果做验证

必须遵守三条纪律：

- 不能使用未来信息
- 不能边回测边改参数
- 不能把不同版本混在一起算结果

## 6. V1 最低可行回测窗口

V1 先不追求复杂的持仓模拟器，而先做最小可行验证：

- 观察窗口：`T+1`、`T+2`
- 重点对象：
  - 昨日候选池 Top10
  - 昨日二次决策 Top3
  - 昨日主仓 / 次仓 / 观察仓
- 重点结果：
  - 红盘率
  - 利润窗口
  - 最大回撤
  - 触发率
  - 劝退准确率
  - 错杀率

这样已经足够发现当前系统的大问题。

## 7. 分层验证：把问题拆成 5 层

V1 回测必须按 5 层验证，不允许只看一个总收益数。

### 7.1 候选池质量

这层验证入口是否把真正值得看的强票放进来了。

重点指标：

- 次日强势股覆盖率
- 全市场最强票进入候选池的比例
- 全市场最强票进入完整排序集 Top10 的比例
- 主线龙头进入候选池的比例

若最强票根本没进候选池，说明问题在入口层，而不是后面的二次决策。

### 7.2 排序质量

这层验证候选池内谁排前面是否合理。

重点指标：

- 主仓是否优于次仓
- 次仓是否优于观察仓
- Top3 是否优于 Top10 平均
- 官方默认组合是否优于“直接按排序前 3”

若好票进了池，但官方组合排错了，问题在排序层。

### 7.3 买点质量

这层验证“票选对了，但给的执行点能不能做”。

重点指标：

- 买点触发率
- 触发后胜率
- 触发后 T+1 / T+2 利润窗口
- 触发后最大回撤
- 偏离过大规则是否真的避开了差位置
- 开盘后 60 分钟内是否给过合理参与机会

若票本身没问题，但买点经常无法触发或触发位置很差，问题在执行层。

### 7.4 总闸门质量

这层验证系统是否过度保守或过度激进。

重点指标：

- 劝退准确率：
  - 系统说“今日不做”时，市场是否真的难做
- 错杀率：
  - 系统说“不做”，但当天强票其实很好做的比例
- 放行准确率：
  - 系统说“可做”时，是否真的存在可执行机会

这一层是当前产品最容易失真的地方。

### 7.5 市场环境适配性

这层验证系统是否只在某些市场条件下有效。

重点指标：

- 强市下胜率 / 利润窗口 / 回撤
- 中性市下胜率 / 利润窗口 / 回撤
- 弱市下胜率 / 利润窗口 / 回撤
- 强市下的错杀率
- 弱市下的误放行率

如果不按市场环境分桶，回测结论会被平均值严重稀释。

## 8. 必须建立的比较基准

不和基准比，回测没有意义。

V1 至少要和以下基准比较：

### 8.1 原始排序基准

- 候选池 Top3 直接等权
- 候选池 Top10 等权

### 8.2 简化规则基准

- 只买主线最强龙头
- 只买每个主线第一名
- 不做二次决策，只看排序结果

### 8.3 空仓基准

- 系统什么都不做

这组基准的作用是回答：

**二次决策到底有没有比“更简单的做法”创造真实增量价值。**

## 9. 赚钱效应样本定义

V1 市场环境层中的“赚钱效应”样本，统一定义为：

- 昨日候选池 Top10
- 昨日二次决策输出的 3 只强票

两者取 **并集去重**。

同时拆成两层：

- `broad_sample`：昨日候选池 Top10
- `core_sample`：昨日二次决策 3 只强票

赚钱效应判断以 `core_sample` 为主、`broad_sample` 为辅，建议权重为：

- `core_effect = 60%`
- `broad_effect = 40%`

这能同时反映：

- 市场广义强势股是否赚钱
- 系统自己最终推荐的强票是否真的更值得做

## 10. 市场环境分桶

V1 回测必须做 regime 分桶，不能只看总平均。

建议直接复用 V1 总闸门中的市场环境层定义，把每个交易日划为：

- `强`
- `中`
- `弱`

分桶后至少看：

- 强市样本中的候选池质量
- 强市样本中的 Top3 表现
- 强市样本中的总闸门错杀率
- 弱市样本中的劝退准确率

一句话总结：

**系统不能只知道“整体好不好”，还必须知道“在哪种市场里好，在哪种市场里坏”。**

## 11. 问题归因树

V1 回测不能只给一个总分，还必须能归因。

建议使用下面这棵归因树：

### 11.1 入口问题

现象：

- 真正最强票没进候选池
- 主线核心票被硬门槛挡掉

定位：

- 候选池入口问题

### 11.2 排序问题

现象：

- 强票进了池，但没进 Top3
- 主仓 / 次仓 / 观察仓顺序失真

定位：

- 评分或二次排序问题

### 11.3 执行问题

现象：

- 票没问题，但买点经常不触发
- 给的区间经常过远、过窄或明显不合理

定位：

- 买点区间 / 触发条件 / 偏离规则问题

### 11.4 总闸门问题

现象：

- 系统天天“仅观察 / 今日不做”
- 但实际市场和核心强票表现并不差

定位：

- 总闸门过于保守

为了把“总闸门过于保守”拆成可验证的问题，V1 回测结果页和单日诊断页不能只展示一个总闸门总分。

至少要同步暴露下面两层信息：

- 区间聚合层：指数趋势、赚钱效应、市场情绪、主线扩散、主线清晰度、组合质量、买点清晰度、角色结构、风险可控度、历史有效性这 10 个模块，各自有多少天成为弱项、其中多少天真的限制了出手、弱项日的真实 T+2 结果如何
- 单日快照层：当天到底是哪几个模块在拖后腿，它们的分数、状态和一句话解释分别是什么

这样回测才能回答：

- 是总闸门整体太保守，还是其中某一个模块长期过于保守
- 某个模块一旦判成“弱”，是否真的对应更差的后续结果
- 后续应该优先校准哪一个模块，而不是笼统地调整个总闸门

### 11.5 市场环境识别问题

现象：

- 系统只在强市或弱市下出错
- 环境判断和真实赚钱效应错位

定位：

- 市场环境层问题

## 12. V1 需要固化的回测指标

为了后续页面、报表和研发对齐，V1 建议先固化以下指标：

### 12.1 候选池层

- `candidate_coverage_rate`
- `leader_in_pool_rate`
- `top10_hit_rate`

### 12.2 排序层

- `top3_vs_top10_alpha`
- `slot_win_rate_main`
- `slot_win_rate_secondary`
- `slot_win_rate_watch`

### 12.3 执行层

- `buy_trigger_rate`
- `buy_signal_win_rate_t1`
- `buy_signal_win_rate_t2`
- `profit_window_t1`
- `profit_window_t2`
- `max_drawdown_after_trigger`

### 12.4 总闸门层

- `do_not_trade_precision`

### 12.5 环境适配层

- `win_rate_bull_regime`

- `false_positive_rate_bear_regime`

## 13. 回测结果如何服务后续进化

V1 可以开始做“自动发现问题”，但 **不能直接自动改规则并上线**。

建议的闭环是：

1. 自动记账  
   - 每天冻结候选池、排序、二次决策、买点、总闸门和真实结果
2. 自动诊断  
   - 按候选池 / 排序 / 执行 / 总闸门 / 市场环境五层归因
3. 自动生成 challenger  
   - 只提出候选改法，不直接替换生产规则
4. 影子回测 / 影子运行  
   - 用同一批历史样本和未来观测窗口验证 challenger
5. Champion / Challenger 决策  
   - 连续通过后，再考虑升级生产版本

一句话：

**V1 可以自动发现问题、自动提出候选改法、自动验证 challenger，但不能自动直接改写现网生产逻辑。**

## 14. V1 最低可行交付

如果只先做第一版，建议最低交付包含：

1. 交易日逐日回放框架
2. 候选池 Top10 与二次决策 Top3 的冻结记录
3. T+1 / T+2 结果回填
4. 五层指标统计
5. 强 / 中 / 弱市场分桶统计
6. 问题归因面板
7. 基准线对比结果

这样已经足够回答：

- 这套方法有没有价值
- 问题主要出在哪一层
- 总闸门是不是过严
- 在什么市场里最容易失真

## 15. 一句话版结论

如果只记这份文档最核心的一句话，可以直接记：

**强势筛选 V1 的回测，不是单纯做收益回测，而是要用统一基线对候选池质量、排序质量、买点质量、总闸门质量和市场环境适配性做分层验证，并据此定位问题层级，为后续受控进化提供依据。**

## 16. 回测任务中心规则（2026-04-17 补充）

为避免重复创建任务、多个任务并发抢算力、用户切页后找不到回测上下文，V1 回测任务中心新增以下产品规则：

### 16.1 任务执行模型

- 全局只允许 `1` 个回测任务处于 `running`
- 其余新任务进入 `queued`
- 队列执行顺序采用 `FIFO`
- 服务重启后，原 `running` 任务自动回退到 `queued`

### 16.2 同参任务复用

以下参数严格相同，视为同一个任务：

- `start_trade_date`
- `end_trade_date`
- `profile`
- `top_n`

若已存在同参任务，则：

- 不再新建任务
- 直接返回已有 `run_id`
- 页面提示：`已存在相同参数任务，已为你定位到该任务`

### 16.3 任务状态

V1 回测任务状态统一为：

- `queued`
- `running`
- `completed`
- `failed`
- `cancelled`

其中：

- `running` 只允许取消，不允许直接删除
- `queued / completed / failed / cancelled` 允许直接删除

### 16.4 取消与删除

- 取消运行中任务：
  - 状态变为 `cancelled`
  - 保留已经完成的日级结果
  - 未完成部分立即停止
- 删除任务：
  - 彻底删除 `run / summary / daily / candidate / decision / outcome`
  - 不保留软删除记录

### 16.5 页面任务中心结构

回测页顶部任务中心采用三段式：

1. 当前运行任务
2. 排队中任务
3. 历史任务

其中历史任务默认只展示最近 `20` 条。

### 16.6 进度刷新与阶段展示

任务中心必须提供 `刷新进度` 按钮。

每条任务至少展示：

- `processed_trade_dates / total_trade_dates`
- 最近更新时间
- 当前阶段

当前阶段采用“交易日 + 阶段”形式，例如：

- `2026-04-08 候选池计算中`
- `2026-04-08 二次决策回放中`
- `2026-04-08 T+1/T+2 结果验证中`
- `区间汇总生成中`

### 16.7 创建任务反馈文案

创建回测时统一使用以下反馈：

- 无运行任务且新建成功：`已创建回测任务，正在后台计算`
- 当前已有任务在运行，新任务入队：`当前已有任务在运行，你的回测已进入队列`
- 存在同参旧任务：`已存在相同参数任务，已为你定位到该任务`
- 取消成功：`任务已取消，已保留已完成部分`
- 删除成功：`任务已删除`
